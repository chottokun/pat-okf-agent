# OKF 設計判断の理由・運用上の落とし穴・開発メモ

本書は、`pat-okf-agent` および OKF（Open Knowledge Federation）知識基盤において、**コードや型定義だけでは読み取れない設計判断の背景・理由**、**古典的検索の到達点**、**運用上で実際に踏んだ落とし穴（Gotchas）**、および**合意済み・未実装の仕様**を記録した開発・保守用リファレンスです。

後から本プロジェクトに触れる開発者やモデルが「改善」のつもりで設計原則を壊したり、議論が完了した仕様を蒸し返したり、既知の落とし穴を再発させたりするのを防止することを目的とします。

---

## 1. 設計判断の理由の記録（Design Rationales）

### 1.1 なぜ `basis` / `ops-record` の形なのか
* **背景**: OKF の核は「検証（validate）を通らない主張は KB に残さない」という証拠ゲートの規律にある。初期の特許中心（EPO/USPTO）から、Web資料、学術論文（arXiv）、そしてエージェント自身の運用記録（手順・作法型）へと知識の対象を拡張するにあたり、出典の信頼性・形式を統一的に機械検証する必要があった。
* **設計理由**:
  1. **契約情報（Tier A）としての厳格性**: `basis` は知識の成立根拠（例: `patent-claim`, `paper`, `ops-record` 等）を示す契約情報であり、表記の揺らぎや未定義値は許容しない。
  2. **P9 の設計（事実と判断の分離）**: 未知の `basis` 値はエラーではなく「警告（P9）」として事実のみを返す。それを致命的（FAIL）として落とすかどうかは、呼び出し側が `--strict-provenance` オプションで決定する。
  3. **機械検証可能なスナップショット（PR #20）**: `ops-record:<パス>#<節> snapshot=<キー>` という形式を定め、KB 内の `evidence/` に置かれたスナップショット（.txt）の実在と sha256 の一致を `okf validate --check-evidence` で機械的に照合する。これにより、運用記録であっても「命名規約まかせの口先リンク」ではなく、原典スナップショットに接地（grounding）された検証可能知識となる。

### 1.2 なぜツール（pat-okf-agent）に「重み」を持たせないのか
* **設計原則**: **「事実に重みを焼き込まない」**（2026-11-12 確定）。
* **設計理由**:
  1. **偏重による自己加速の防止**: 「偏重的な重みは、間違いに進むと加速度的に間違う」（オーナー原則）。キーワードや概念にツール側で固有の「重要度」「深刻度」といった固定の重みを焼き込むと、文脈の変化に対応できず、誤った前提が次の探索や証拠収集を歪めて誤りを自己強化してしまう。
  2. **ツール＝事実の観測器**: ツール（`candidate-check`、`search`、`validate`）は、出現回数・リンク関係・一致箇所などの「客観的事実（relations / hits / counts）」のみを返す。
  3. **重み付けは判断の層へ**: その事実をどう評価するか（合否判定、優先度、採用判断）は、ツールではなく上位のスキル文書、実行プロンプト、あるいは人間の判断層（`--fail-on` 等）に委ねる。

### 1.3 なぜ cap／再開などのエンジン固有の都合を OKF 本体に入れないのか
* **設計原則**: **「エンジン（LLM）は交換可能な部品」**（Stage-3 方針）。
* **設計理由**:
  1. **ハーネスとエンジンの分離**: 設計は強いモデル、実装は Flash、量産は OpenCode というように、実行エンジンは随時切り替えられる。エンジンのコンテキスト長制限（cap）、レートリミット対策、途中再開ロジックといった都合を OKF のコアデータ構造やツール本体に焼き込むと、エンジンの交代・進化によってツール側が陳腐化・複雑化する。
  2. **品質はゲートと監査で担保**: 特定エンジンの振る舞いや賢さに頼るのではなく、客観的な証拠ゲート（`validate`、`check-evidence`）と独立した監査記録によって知識の品質を保証する。

## 2. 検索の到達点と評価の置き方（Search Scope & Evaluation）

### 2.1 到達点の確定：古典的キーワード検索の完成
* **オーナー定義**:
  > **「キーワード検索に AND / OR とワイルドカード（*）が備われば、検索機能としては古典的に実装完了とする。」**
* **到達点の内訳（PR #15 〜 PR #18、PR #22 で完了）**:
  1. **文字包含の原則**: 検索の核は文字包含（部分一致）。一致した場所（タイトル、タグ、見出し、本文）にのみ重みを置く。
  2. **古典的構文のサポート**:
     * 明示的 `AND` / `OR` 演算子（例: `A AND B`, `A OR B`）。
     * 前方一致ワイルドカード `*`（例: `thermo*`）。
  3. **ASCII/英語耐性**:
     * Typo フォールバック（レーベンシュタイン距離による類似語救済）。
     * 軽微な語尾・活用形正規化（複数形 `-s`/`-es`、動名詞 `-ing`、過去形 `-ed`）。
     * 大文字・小文字の完全同一視（`casefold`）。
  4. **因果が読めるスコア内訳（Breakdown）**: スコアの合計値が各フィールドの寄与と完全に一致する不変条件（PR #17）。
  5. **グラフヒント**: 引用数（`outgoing_links`）と被リンク数（`backlinks`）をメタデータとして付与。ただし検索スコアの加減算には一切使用しない（PR #22）。
* **境界線（これ以上の改良を行わない理由）**:
  * 道具としての検索機能はこれで完成形。意味の解釈や高度なリランキングを道具側に抱え込ませず、読み手（モデル・エージェント）の層に置く。むやみなセマンティック検索化やアルゴリズム変更で壊さないこと。

### 2.2 評価プローブの置き場と経緯
* **プローブの置き場**: 各 KB の直下に `eval_queries.json` を配置する（例: `kb-semiconductor-thermal/eval_queries.json`, `kb-ai-research/eval_queries.json`）。
* **初期未達の経緯と改善プロセス**:
  * 初期のベースライン測定（12プローブ）では Top-1 25% / Top-3 33% と大幅に低迷していた。
  * 原因: 単純カウントによる長文有利、一致フィールドの軽視、英語トークンの完全一致依存。
  * PR #15（フィールド加重・スコープフィルタ）で Top-1 50% / Top-3 66.7% に改善。
  * PR #16（Typo/活用形/演算子）により、KB#2 の 34 クエリ評価では **34/34 全件が対象概念を1位（Top-1 100%）** で通過する到達点に到達した。

## 3. 運用上の落とし穴リスト（Gotchas & Pitfalls）

実際に環境構築や運用・監査で踏んだ事実と対策のリストです。

### 3.1 `check-evidence` は `--evidence-dir` の明示が必須
* **現象**: `okf validate --check-evidence` をディレクトリ指定なしで実行すると、デフォルトでカレントディレクトリの `data/external/source_verify` を見に行く。
* **影響**: KB 内に `evidence/` を持つ独立型 KB（運用記録型や論文中心型など）を検証すると、スナップショットが全件 missing（E1）となり、別 KB 側の孤立証跡（orphan）が大量に報告されて検証に失敗する。
* **対策**: 必ず `--evidence-dir <KBディレクトリ>/evidence` を明示して実行すること。
  ```bash
  okf validate --strict-provenance --check-evidence --evidence-dir <path-to-kb>/evidence <path-to-kb>
  ```

### 3.2 テストスイートは `pytest` ではなく `unittest discover`
* **現象**: 開発環境やCIで `pytest` コマンドを実行しようとすると、`pytest: コマンドが見つかりません` または起動不可となる場合がある。
* **理由**: 本プロジェクトは外部依存ゼロ（標準ライブラリのみで動作）を基本としており、テストフレームワークは Python 標準の `unittest` を使用している。
* **対策**: テストコード内で `pytest` を import しないこと。実行は以下を使用する：
  ```bash
  python3 -m unittest discover tests
  # または .venv 内の Python を指定
  .venv/bin/python3 -m unittest discover tests
  ```

### 3.3 クラウドドライブ（rclone 等）マウント時のコールドアクセス遅延
* **現象**: クラウドストレージをマウントしたディレクトリ配下の KB に対して `okf validate` や `find` を実行した際、数十秒〜数分間応答がないことがある。
* **理由**: rclone マウント（VFS キャッシュ full）等のコールド走査（初回ディレクトリツリー読み出し）に時間がかかるため（実測: コールド数百秒、キャッシュ温まり後は 1 秒未満）。
* **対策**: フリーズやハングアップではないため、強制終了（kill）せずに待つこと。また、同期直後の照合にはマウント経由ではなく `rclone copy` ＋ `rclone check` によるリモート直接照合を用いること。

### 3.4 KB 配下の `.md` ファイル走査仕様
* **現象**: KB 内の `evidence/` や作業用サブディレクトリに説明用の `.md` を置くと、`okf validate` が壊れたノートとして検知してエラーになる。
* **理由**: `okf validate` は指定ディレクトリ配下のすべての `*.md` を概念ノードとしてパースする仕様。
* **対策**: 証跡スナップショット、ログ、生テキストは必ず `.txt` や `.json` などの非 `.md` 拡張子で保存すること。

## 4. 決定済み・未実装のメモ（Decided but Unimplemented）

仕様や方針は合意済みだが、コード未実装の項目です。実装時に設計を蒸し返さないこと。

### 4.1 `okf verify-source --file`（実装済み）
* **決定済みの位置づけ**: **「利用者が渡したローカル素材のインテイク口」**。保証するのは「受け取ったバイト列の同一性」であり、素材の出所自体の真偽は保証しない。
* **実装された仕様**:
  * 外部 URL からの HTTP 取得を行わず、手元にあるローカルファイル（PDF、HTML、TXT、Markdown 等）を `--file` 引数に取る。
  * ファイルの sha256 を計算し、`local_<sha256[:16]>` をキーとして指定の証跡ディレクトリ（`snapshots/` 等）へ保全コピー・`.extracted.txt`・`.meta.json` サイドカーを生成する。
  * **Markdown 素材の拡張子保護**: `.md` / `.markdown` 素材は §3.4 の対策に従い、本体コピーを `.txt` として保存して `okf validate` の誤検知を防ぐ（元拡張子は `.meta.json` の `original_ext` に保持）。
  * **内容ハッシュ共有時のファイル名扱い**: 同一内容・別ファイル名の素材を取り込んだ場合、ハッシュキー `local_<sha256[:16]>` が一致するためスナップショットを共有し、`.meta.json` の `original_filename` には最初に取り込んだ名前が残る。
  * **出典形式**: `local-file:<無空白ファイル名> retrieved=YYYY-MM-DD via=local-file snapshot=local_<sha256[:16]>`（`--issued` 指定時のみ `issued=YYYY-MM-DD` を付与。角括弧等の修飾は付かない）。`okf validate --check-evidence` で `ops-record` と同じ `snapshot=` 機構で検証される。

### 4.2 Traversal（グラフ探索）のエンドツーエンド検証
* 検索結果（起点）から Markdown 相対リンクを辿ってコンテキストを収集する `traversal` 機能について、実運用での包括的ベンチマーク（エンドツーエンド検証）は今後の課題として残されている。

### 4.3 `okf links` 診断と `LinkScan`（未リンクの素テキスト slug 検出）
* **到達性診断（実装済み）**: 孤立ノード、被参照 0 件（`zero_inbound`）、発リンク 0 件（`zero_outbound`）、弱連結成分、`--from <seed>` 起点からの到達不能ノートを事実として返す `okf links`（既定 `--no-admin`）を `pat-okf-agent` 本体へ実装済み。
* **未リンク素テキスト検出（保留）**: 外部の作業用バッチランナー側で先に `LinkScan` の実装・運用実績を積み、全 KB 共通の読み取り専用機能（`okf links --unlinked` 等）として有用性が確定した段階で本流への昇格を判断する。

### 4.4 KB ビューア向け JSON エクスポート（`scripts/export_kb_viewer_all.py` → `okf export` 正式化済み）
* **実装された正式仕様**: `okf export <dirs>... --out <file> [--label ...] [--cache-dir ...] [--format-version 1|2] [--scope all|concepts|patents] [--json]` として本体 CLI へ実装済み（既定 `format_version=2`）。
  * `concepts` は各フォルダ `index.md` のリンク出現順に並び、未掲載ノートはファイル名順で末尾に補完する。
  * `sources` 行の `genre=` 属性（未指定時は `kind` から `paper` / `patent` / `web` / `other` を自動解決）に基づき、`genre=paper` の出典を `papers[]` として第一級レコード化し、`concepts[].paper_ids`・`papers[].related_concepts` の双方向参照を出力する。
  * 決定論性とオフライン動作を保つため、書誌解決はローカルの `evidence/` とキャッシュディレクトリのみを参照し、未キャッシュやタイトル欠落の論文は最小レコード（`title: null`）＋ `warnings` として明示する。
* **移行互換**: `format_version=1` および `--scope`（`all` / `concepts` / `patents`）により先行プロトタイプ（`scripts/export_kb_viewer_all.py`）との後方互換を維持している。

## 5. 外部記憶・監査記録の分離方針（Records Pointer）

KB 本体および構築・監査記録の正本は、ツールリポジトリ（`pat-okf-agent`）内ではなく、外部の KB ストレージ（クラウドドライブ等）に分離して管理する運用を推奨します。

* **構成方針**: KB 本体ディレクトリと同列の `records/` 等に、設計メモ・バッチ監査記録・評価結果を保存する。
* **ファイル命名規則（推奨例）**:
  ```text
  okf-<トピック/対象>-<文書種別>-<日付(YYYY-MM-DD)>.md
  ```
* **リポジトリ側での扱い**: ツール本体リポジトリには個別の KB 構築ログや監査実体を二重保持せず、設計根拠・公開可能な原則のみを維持する。
